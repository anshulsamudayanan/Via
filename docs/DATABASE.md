# VIA Database

PostgreSQL 16. SQLAlchemy 2 models in `apps/api/src/via_api/models/`, Alembic
migrations in `apps/api/src/via_api/migrations/` (bundled in the package, so they
run from source checkouts and Docker images alike).

## Conventions
- **Primary keys:** UUID (`uuid4`, generated by the application).
- **Timestamps:** `timestamptz`; sessions run with `timezone=UTC`. `created_at` on every table, `updated_at` on mutable ones.
- **Enums:** `VARCHAR(32)` + `CHECK` constraint (not native Postgres enums), so adding a value is a simple migration.
- **Constraint names:** deterministic (`pk_`, `fk_`, `uq_`, `ix_`, `ck_` prefixes), so migrations are stable and reviewable.
- **Deletes:** owned data cascades (project → designs → revisions → files, PCB rows). Audit data survives (`SET NULL`). Users who own projects can't be hard-deleted (`RESTRICT`).
- **No file contents in PostgreSQL:** `design_files` stores only metadata and an object-storage key.

## Migrations

```bash
via-api migrate                                   # upgrade to head (prints before -> after)
cd apps/api && alembic revision --autogenerate -m "describe change"   # then review by hand
cd apps/api && alembic check                      # fails if models and migrations differ
```

`tests/integration/test_migrations.py` runs upgrade → downgrade → upgrade on a real
database, asserts the models match the migrations (`compare_metadata` reports no
differences), and checks UUID keys, timezone-aware timestamps, indexed foreign keys
and key constraints.

Note on `0001`: `designs.current_revision_id` ↔ `design_revisions.design_id` is a
circular reference. The FK on `designs` is added with `ALTER TABLE` after both
tables exist (hand-edited after autogenerate).

Revisions: `0001` initial schema, `0002` `design_revisions.summary`, `0003` job lifecycle columns on `analysis_runs`, `0004` analysis findings, `0005` manufacturing profiles, `0006` AI outputs, recommendations, component records, `0007` optimization candidates and design changes.

## Tables (revision 0001, with later additions noted)

### Identity & organizations
| Table | Purpose | Key columns / constraints |
|---|---|---|
| `users` | Accounts | `email` unique (stored lower-cased), `password_hash` (Argon2id from CP3), `display_name`, `is_active`, `email_verified_at`, `last_login_at` |
| `user_sessions` | Server-side sessions | `token_hash` unique (SHA-256 of the cookie token; the token itself is never stored), `expires_at` (indexed), `revoked_at`, `ip_address`, `user_agent` |
| `password_reset_tokens` | Reset foundation | `token_hash` unique, `expires_at`, `used_at` (single use) |
| `organizations` | Owners of projects | `slug` unique, `is_personal` (every user gets one on registration) |
| `organization_memberships` | Org roles | unique `(organization_id, user_id)`, `role` ∈ owner/admin/member |

### Projects
| Table | Purpose | Key columns / constraints |
|---|---|---|
| `projects` | Workspace for designs | `organization_id` (RESTRICT), `owner_id` (RESTRICT), `visibility` ∈ private/organization, **default `private`** (also a server default), `archived_at`, index on `(organization_id, lower(name))` |
| `project_memberships` | Explicit project access | unique `(project_id, user_id)`, `role` ∈ owner/editor/viewer, `added_by_id` |

### Designs & files
| Table | Purpose | Key columns / constraints |
|---|---|---|
| `designs` | A board within a project | `project_id`, `current_revision_id` (latest parsed revision) |
| `design_revisions` | One upload + its parse outcome | unique `(design_id, revision_number)`, `project_id` (denormalized for authorization), `status` ∈ pending/processing/ready/failed (indexed), `source_format`, `source_sha256`, `parser_version`, `schema_version`, `imported_at`, `error_code`, `error_message` (safe text only), `warnings` (JSONB), `object_counts` (JSONB) |
| `design_files` | Object-storage metadata | `kind` ∈ source/normalized, `storage_key` unique (server-generated), `sha256`, `size_bytes`, `content_type`, index `(project_id, sha256)` |
| `upload_records` | Every upload attempt | `outcome` ∈ accepted/rejected/duplicate, `rejection_reason`, `sha256`, `ip_address`; index `(project_id, created_at)` |

Duplicate detection (CP4): `(project_id, source_sha256)` on `design_revisions` is indexed.

### Parsed PCB projections
The full normalized design (every track, pad and graphic) is stored as JSON in object
storage. These tables hold what the API paginates, searches and summarizes:

| Table | Rows | Notes |
|---|---|---|
| `pcb_layers` | one per layer | unique `(revision_id, name)` |
| `pcb_nets` | one per net | per-net pad/track/via counts and track length; index `(revision_id, lower(name))` |
| `pcb_components` | one per footprint | reference, value, footprint, layer/side, x/y/rotation, attributes/properties (JSONB); index `(revision_id, lower(reference))` |
| `pcb_geometry` | one per revision | bbox, width/height/area, thickness, copper layer count, `normalized_file_id` → `design_files` |

### Processing, audit, consent
| Table | Purpose | Notes |
|---|---|---|
| `analysis_runs` | Processing runs | `kind = pcb_import` (Stage 1) or `pcb_analysis` (Stage 2); status queued/running/succeeded/failed, timings, safe error, `result_summary`. Since `0003`: `attempt` (1 = first try), `job_id` (queue job of the current attempt), `heartbeat_at` (refreshed every `VIA_JOB_HEARTBEAT_SECONDS` while running); index `(kind, status)` for the reaper |
| `activity_logs` | Activity feed + security audit | append-only; `project_id`/`organization_id` are SET NULL on delete so entries outlive their subject; `target_id` has no FK; indexes `(project_id, created_at desc)`, `(actor_id, created_at desc)`, `(action)` |
| `data_consents` | Explicit, revocable consent | `scope` ∈ via_learn_contribution / external_ai_processing, `policy_version`, `granted_at`, `revoked_at`. No row = no consent. Since CP5, project owners can grant/revoke `external_ai_processing` (`/api/v1/ai/consent/{project_id}`), and the AI context provider requires it; `via_learn_contribution` is used by VIA Learn (`/projects/{id}/learn-consent`). |

## Authorization model (enforced in the API service layer, CP3+)

Organization membership and project membership are **independent**:

| Who | Private project | Organization-visible project |
|---|---|---|
| Project owner | owner | owner |
| Project member | their project role | their project role |
| Organization member/admin/owner (not a project member) | **no access** (404) | viewer |
| Anyone else | no access (404) | no access (404) |

- Being an organization admin never grants access to private projects. Being a project member never grants organization rights.
- Inaccessible projects return `404`, not `403`, so their existence isn't revealed.
- Every query for project-scoped data (designs, revisions, files, PCB rows, analysis runs, project activity) filters through the accessible-project check. `project_id` is denormalized onto revisions and files to keep that check a single indexed lookup.

## VIA Learn (implemented, migration 0011)

Full description in [VIA_LEARN.md](VIA_LEARN.md). Summary:

- `recommendation_feedback` and `ai_output_knowledge` are project-scoped and follow project access.
- `learn_entries` and `learn_entry_versions` are the collective store: foreign keys only to `users`, `data_consents` and each other, never to projects, designs, revisions or files. Search uses a GIN-indexed `tsvector`.
- A contribution derived from a project needs an active `via_learn_contribution` consent from the owner plus a per-item submit. Withdrawal erases content but keeps id, ownership and provenance.
- `users.learn_reviewer` is set only through the server CLI.
- Not done: a separate database role for the collective tables.
- Defaults: no consent rows, no contributions, nothing collected automatically.
